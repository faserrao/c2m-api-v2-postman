# Config Files Reference

This document describes every active file in `config/`. The EBNF Data Dictionary
(`data_dictionary/c2mapiv2-dd.ebnf`) is the ultimate source of truth. Config files
either **derive from it automatically** (generated on every build) or are **manually
maintained** and must stay in sync with it.

### `faker_hints.yaml`

**Purpose:** Provides realistic placeholder values for every field used across the
Getting Started collections. One hint per DD rule name. Three hint strategies are
supported: call a Faker.js method, use a fixed static value, or pick a random integer
in a range.

**Generated by:**
- Script: `scripts/active/ebnf_to_openapi_dynamic_v3.py`
- CLI arg: `--faker-hints-output config/faker_hints.yaml`
- Make target: `make openapi-build` → `make generate-openapi-spec-from-ebnf-dd`
- Source: `@hint` annotations embedded directly in `data_dictionary/c2mapiv2-dd.ebnf`
  (e.g. `firstName = string ; (* @hint faker first_name *)`)

**To change a hint:** Edit the `@hint` annotation on the relevant rule line in the
EBNF DD, then run `make openapi-build`. Commit both the DD and this file together.

**Used by:**
- `scripts/utilities/generate_getting_started_collections.py` via `--faker-hints`
  (replaces `<String>`/`<Integer>` placeholders in the linked Getting Started collection)
- `scripts/validation/validate_configs_against_dd.py` (`make validate-configs`)
  (validates that every key in this file is a known DD rule name)

**YAML structure:**

```yaml
# DO NOT EDIT — update the @hint annotation in the EBNF Data Dictionary instead.
faker_hints:
  <rule_name>:
    type: faker          # calls a Faker.js method by name
    method: <method>     # e.g. first_name, city, state_abbr, zipcode, company

  <rule_name>:
    type: static         # always emits this exact value
    value: <value>       # string, integer, or boolean

  <rule_name>:
    type: random_int     # picks a random integer in [min, max]
    min: <int>
    max: <int>

  <rule_name>:
    type: aba_routing_number   # special type for ABA routing numbers
```

**Hint type reference:**

| Type | When to use | Example fields |
|---|---|---|
| `faker` | Human-readable variable data (names, addresses) | `firstName`, `lastName`, `city`, `state`, `zip`, `address1`, `company` |
| `static` | Canonical enum values and fixed test data | `mailClass`, `color`, `cardType`, `cardNumber`, `cvv`, `month`, `year`, `layout` |
| `random_int` | Numeric IDs that vary per run | `documentId`, `requestId`, `zipDocumentId`, `addressListId`, `mappingId` |
| `aba_routing_number` | Valid ABA routing numbers | `routingNumber` |

**Hardcoded values that must stay:** None. This file is fully derived from the DD.

### `c2m_provider_mappings.yaml`

**Purpose:** Maps every canonical `jobOptions` enum value (as defined in the EBNF DD)
to the literal string accepted by the Click2Mail provider. For this API the canonical
value and provider literal are identical (pass-through mapping), so this file acts as a
machine-readable registry of valid enum values plus a merge point for legacy aliases
defined in `c2m_provider_aliases.yaml`.

**Generated by:**
- Script: `scripts/active/ebnf_to_openapi_dynamic_v3.py`
- CLI args: `--provider-mappings-output config/c2m_provider_mappings.yaml
  --provider-aliases config/c2m_provider_aliases.yaml`
- Make target: `make openapi-build` → `make generate-openapi-spec-from-ebnf-dd`
- Source: enum values read from `components.schemas` in the freshly generated OpenAPI
  spec (which itself was generated from the EBNF DD moments earlier), then aliases
  merged from `c2m_provider_aliases.yaml`

**To add a new jobOptions enum value:** Add it to the EBNF DD and run `make openapi-build`.
The new value will appear automatically.

**To add a new alias:** Edit `c2m_provider_aliases.yaml` (see below) and run
`make openapi-build`.

**Used by:**
- `scripts/validation/tests/test_dd_constraints.py` — golden test suite verifies that
  every EBNF enum value has a mapping entry, no extra non-EBNF values exist, and every
  alias target is a valid canonical value

**Not used** in the production collection build pipeline — it is a test-support and
reference file consumed by validation tooling only.

**YAML structure:**

```yaml
# Generated by ebnf_to_openapi_dynamic_v3.py — DO NOT EDIT.
# Canonical values are derived from the EBNF Data Dictionary (c2mapiv2-dd.ebnf).
# To add/change aliases, edit config/c2m_provider_aliases.yaml and re-run make openapi-build.

<field_name>:
  <canonical_value>: <provider_literal>   # for this API, always canonical == provider
  <canonical_value>: <provider_literal>
  _aliases:                               # merged from c2m_provider_aliases.yaml
    <legacy_string>: <canonical_value>
    "<display string>": <canonical_value>
```

**Fields covered:** `mailClass`, `color`, `paperType`, `printOption`, `productionTime`,
`envelope`, `documentClass`, `layout`.

**Hardcoded values that must stay:** None. This file is fully derived from the DD and
the aliases file.

### `c2m_provider_aliases.yaml`

**Purpose:** Contains only the `_aliases` blocks for `jobOptions` fields — human
knowledge about legacy string names, display labels, and variant spellings that external
systems or older catalogs may send. These are merged at build time into the generated
`c2m_provider_mappings.yaml`.

**Maintained by:** Human editors only. Do NOT put canonical DD values here — those are
derived automatically. Only put non-canonical legacy strings that need to be normalised
to a canonical value.

**Validated by:**
- `test_provider_aliases_values_are_canonical` in `test_dd_constraints.py` — every
  alias target must be a valid EBNF enum value; build fails if an alias points to a
  non-existent canonical value

**Used by:**
- `ebnf_to_openapi_dynamic_v3.py` at build time via `--provider-aliases` — merged into
  the generated `c2m_provider_mappings.yaml`

**When to update this file:**
- A provider starts sending a new display string or legacy alias
- A catalog entry uses a non-canonical form that needs normalisation
- A human-readable label must be accepted alongside the canonical snake_case value

**YAML structure:**

```yaml
<field_name>:
  _aliases:
    <legacy_or_display_string>: <canonical_dd_value>
    "<string with spaces>":     <canonical_dd_value>
```

**Current aliases and rationale:**

| Field | Alias | Maps to | Why it exists |
|---|---|---|---|
| `mailClass` | `firstClass` | `first_class` | camelCase legacy form from pre-GA catalog |
| `mailClass` | `"First Class"` | `first_class` | Display label used in some UI surfaces |
| `mailClass` | `"Standard"` | `standard` | Title-case display label |
| `color` | `fullColor` | `full_color` | camelCase legacy form from pre-GA catalog |
| `color` | `"Full Color"` | `full_color` | Display label |
| `color` | `"Black & White"` | `black_and_white` | Display label with ampersand |
| `color` | `grayscale` | `black_and_white` | Alternative term accepted as synonym |
| `paperType` | `"White 24#"` | `white_24` | Display label with weight notation |
| `paperType` | `"Glossy"` | `glossy` | Title-case display label |
| `printOption` | `printing_one_side` | `single_sided` | Legacy snake_case name |
| `printOption` | `printing_both_sides` | `double_sided` | Legacy snake_case name |
| `printOption` | `"Double Sided"` | `double_sided` | Display label |
| `printOption` | `"Single Sided"` | `single_sided` | Display label |
| `envelope` | `"#10 double window"` | `double_window` | Industry notation |
| `envelope` | `windowed` | `double_window` | Legacy name used in `error-response-examples.yaml` prior to Sep 2026 |
| `layout` | `address_on_top` | `address_on_first_page` | Legacy name retired before GA |

**Hardcoded values that must stay:** All alias **keys** (left side) are inherently
hardcoded — they are the legacy strings being normalised. All alias **targets** (right
side) must be valid DD enum values and are enforced by the golden test suite.

### `curated-examples-catalog.yaml`

**Purpose:** Single source of truth for every curated example that appears in the
Real World Use Cases and Getting Started Postman collections. Defines which endpoints
appear, which oneOf branches to materialise, and what leaf values to inject.

**Validated by:**
- `scripts/validation/validate_configs_against_dd.py` — validates all `values:` key
  names against DD rule names (`make validate-configs`)
- `scripts/validation/validate_catalog_against_spec.py` — validates `select:` keys and
  variant names against the live OpenAPI spec (`make validate-catalog-against-spec`)
- `scripts/validation/validate_configs_against_dd.py` — V3a: validates `values:` keys;
  V3b: validates `select:` entries against spec oneOf variants

**Used by:**
- `Makefile` targets `postman-generate-real-world-collection`,
  `postman-generate-getting-started-linked-collection`
- `scripts/utilities/generate_getting_started_collections.py` via `--config`

**YAML structure:**

```yaml
groups:                          # Postman folder definitions (Getting Started only)
  - logical_name: most-frequently-used    # referenced by examples[].group
    display_name: Most Frequently Used    # Postman folder label
    order: 1                              # folder sort order
    description: ...

examples:
  - name: Legal Firm - Court Notices      # display name in Postman
    method: POST
    path: /static                         # API endpoint path
    group: most-frequently-used           # links to a group above (getting-started tag only)
    tags:
      - real-world                        # "real-world" → appears in Real World collection
      - getting-started                   # "getting-started" → appears in Getting Started
    description: ...
    select:
      docSourceAll: documentIdSource      # oneOf branch selector: key=discriminator field,
      recipientAddressSource: singleAddress  # value=branch variant name in spec
      paymentDetails: creditCard
    values:                               # FLAT leaf primitives only
      jobTemplate: standard_letter
      tags:
        - legal
        - certified
```

**Key rules:**
- `values:` must contain **flat leaf primitives only** — no nested objects. The
  generator reads request structure from the Linked Collection.
- All keys in `values:` must be valid EBNF DD rule names (enforced by
  `validate_configs_against_dd.py`).
- `select:` keys and variant names are validated against the OpenAPI spec.
- The `group:` field is only used for entries tagged `getting-started`.

**Hardcoded values that must stay and why:**

| Value(s) | Location | Why hardcoded |
|---|---|---|
| `jobTemplate: standard_letter`, `legal_certified_mail`, etc. | Various examples | `jobTemplate` is `type: string` with no enum in the spec — names are customer-defined per account. Values here are illustrative only and not spec-validated. |
| `documentId: 11111`, `22222`, `3001`, etc. | `mergeDocumentSource` arrays in merge examples | Specific IDs chosen to tell a coherent story for each business scenario (Medical Agency patient records, Marketing Agency campaign, etc.). Deliberately non-random. |
| `startPage: 1`, `endPage: 3` | Split-PDF examples | Illustrative page range for the split operation. |
| Tags arrays (`- legal`, `- certified`, etc.) | All examples | Organizational metadata strings — not DD values, no enum exists for them. |
| `filename: invoice_001.pdf`, `letter_001.pdf`, etc. | ZIP batch examples | Illustrative filenames specific to the business scenario. |
| `mergeByDocumentId`, `mergeByRequestId` inline structures | Merge examples | These are oneOf branch structures that must be authored explicitly; the generator cannot infer which merge strategy to demonstrate. |

**Known hardcoded DD enum values (pending fix):**

The "Using jobOptions Instead of Template" example (lines 423–431) contains 8 explicit
`jobOptions` enum values that duplicate DD enum values:

```yaml
jobOptions:
  documentClass: letter           # DD enum — matches faker_hints
  layout: address_on_first_page   # DD enum — matches faker_hints
  productionTime: standard        # DD enum
  envelope: double_window         # DD enum
  color: full_color               # DD enum — matches faker_hints
  paperType: white                # DD enum — matches faker_hints
  printOption: double_sided       # DD enum — matches faker_hints
  mailClass: first_class          # DD enum — matches faker_hints
```

These are intentionally educational (showing real enum values to the user), but they
have no validation gate against the DD and will silently drift if the DD enum changes.
**No fix applied yet** — tracked as a future improvement.

### `getting-started-template.yaml`

**Purpose:** Defines the folder structure, endpoint list, and per-request field
placeholder layout for the Getting Started collections. The structural complement to
`curated-examples-catalog.yaml` — the catalog provides realistic values for curated
scenarios; this template defines which endpoints appear and their structural shape for
the bootstrap/educational collections.

**Validated by:**
- `scripts/validation/validate_configs_against_dd.py` — V3a: validates `values:` key
  names; V3b: validates `select:` entries against spec oneOf variants

**Used by:**
- `scripts/utilities/generate_getting_started_collections.py` via `--template`
- `Makefile` target `postman-generate-getting-started-with-examples`

**YAML structure:**

```yaml
collection:
  name: C2M API v2 - Getting Started
  description: ""
  version: 1.0.0

schema_references:
  openapi_spec: openapi/c2mapiv2-openapi-spec-final.yaml
  linked_collection: postman/generated/c2mapiv2-linked-collection-flat.json
  note: ...

groups:
  - logical_name: most-frequently-used
    display_name: Most Frequently Used
    order: 1
    description: ...

examples:
  - name: /static - single or list of recipient
    method: POST
    path: /static
    group: most-frequently-used
    tags: []
    description: ...
    select:
      docSourceAll: requestIdSource
      recipientAddressSource: recipientAddressByList
    values:
      jobTemplate: <String>          # placeholder — faker_hints provides a real value
      pdfSplitJobsNoAddress:
        - jobTemplate: <String>
          startPage: <Integer>
          endPage: <Integer>
      jobOptions:
        documentClass: <String>      # placeholder — no hardcoded enum value
        layout: <String>
        ...
```

**Key rules:**
- All `values:` entries use type placeholders (`<String>`, `<Integer>`) — no hardcoded
  enum values. The linked collection generator replaces these with faker_hints values;
  the test collection generator uses `addRandomDataToRaw.js`.
- The `faker_hints:` section was removed from this file in September 2026; hints now
  live in the EBNF DD as `@hint` annotations and are derived into `faker_hints.yaml`.
- The `groups:` list controls the Getting Started folder layout (separate from the
  `groups:` list in `curated-examples-catalog.yaml`).

**Hardcoded values that must stay:** None. All values are type placeholders (`<String>`,
`<Integer>`). This file contains no hardcoded DD enum values.

### `error-response-examples.yaml`

**Purpose:** Single source of truth for all HTTP error response examples injected into
the OpenAPI spec and Postman collections. Defines one or more named examples per HTTP
status code, each with a fixed `errorCode`, human-readable `errorMessage`, and an
`errorDetails` JSON string.

**Validated by:**
- `scripts/active/add_response_examples.py` — validates `errorCode` values against the
  DD `errorCode` enum at runtime; exits with error on any unknown code

**Used by:**
- `scripts/active/add_response_examples.py` — injects examples into the OpenAPI spec
- `scripts/active/add_error_responses_to_collection.js` — injects examples into
  Postman collection responses

**YAML structure:**

```yaml
# Top-level keys are HTTP status codes as integers
400:
  <example_name>:                        # slug used internally; not shown in Postman
    summary: "Short description"         # shown as the example name in Postman/spec
    errorMessage: "Human-readable text"  # goes into response body errorMessage field
    errorCode: SOME_ERROR_CODE           # must match EBNF DD errorCode enum exactly
    errorDetails: '{"key": "value"}'     # JSON string; supports {timestamp} and {expired} tokens

401:
  missing_token:
    summary: "Missing authentication"
    errorMessage: "Authorization header is missing or invalid"
    errorCode: MISSING_AUTH_HEADER
    errorDetails: '{"expected": "Bearer <token>", "received": "none"}'
```

**Template tokens in `errorDetails`:**

| Token | Replaced with |
|---|---|
| `{timestamp}` | Current UTC time (ISO 8601) |
| `{expired}` | One hour ago (for token-expiry context) |
| `{requestId}` | Generated request ID |
| `{supportEmail}` | Support contact email |

**Fields NOT included here (derived at injection time):**

| Field | Source |
|---|---|
| `errorType` | Derived from `x-http-error-map` in the OpenAPI spec |
| `errorTrackingId` | Generated dynamically per invocation |

**HTTP status codes covered:** 400, 401, 403, 404, 422, 429, 500.

**Hardcoded values that must stay and why:**

| Value(s) | Why hardcoded |
|---|---|
| `errorCode:` values (`MISSING_REQUIRED_FIELD`, `INVALID_TOKEN`, etc.) | The scenario → errorCode mapping is human-curated knowledge that cannot be derived from the DD alone. The DD defines the valid code enum; this file decides which scenario uses which code. Validated at runtime against the DD so drift is caught at build time. |
| `errorMessage:` strings | Human-authored display text. No machine-derivable equivalent exists. |
| `errorDetails:` JSON content | Human-authored contextual detail. Cannot be derived. |
| `summary:` strings | Human-authored display name for each example. Cannot be derived. |

**Known hardcoded DD enum value (no validation gate):**

In the 422 `invalid_enum_value` example, the `allowed` array inside the `errorDetails`
JSON string hardcodes `mailClass` enum values from the DD:

```yaml
errorDetails: '{"field": "mailClass", "provided": "express", "allowed": ["first_class", "standard", "non_profit"]}'
```

This is illustrative content embedded inside a JSON string within YAML, which makes
automated derivation complex. It will silently drift if the `mailClass` enum changes.
**No fix applied yet** — tracked as a future improvement.
